# Администрирование · Сегменты и политики ndm (policy-v2)

> 🔴 **Главные грабли интеграции.** Политика ndm, назначенная сегменту,
> действует на все его устройства; привязка устройства перекрывает привязку
> сегмента. Это конфигурация ndm, а не kgate.

## 🧭 Модель (policy-v2, семантика 09.11)

Деплой создаёт РОВНО ДВЕ политики:

| Политика | Состав | Поведение привязанного |
|---|---|---|
| **VPN** | permit Proxy0, запрет ISP | через туннель (таблица политики несёт дефолт Proxy0) |
| **NO-VPN** | permit ISP, запрет Proxy0 | напрямую через провайдера, туннель не участвует |

**Честный дефолт:** Proxy0 стоит `ip global 1200` (ISP 1000 забирает дефолт),
поэтому устройство/сегмент БЕЗ привязки ходит НАПРЯМУЮ. Привязка решает всё:

| Объект | Привязка | Поведение |
|---|---|---|
| устройство (host) | VPN | в туннеле при любом дефолте |
| устройство (host) | NO-VPN / без привязки | напрямую (fail-safe дом) |
| сегмент (Bridge) | VPN | весь сегмент в туннеле, кроме устройств с собственной привязкой |
| сегмент (Bridge) | NO-VPN | сегмент напрямую (IoT/гости), индивидуальные привязки перекрывают |

Segment id как его знает ndm — имя моста/точки доступа (`Bridge0`="Home",
`Bridge1`="LAN", `Bridge2`="SMART" на Ultra; видно в `show ip hotspot`).

Legacy-эскейпы v1 (`VPN-TV`, `VPN-Laptops-Phones`, `DIRECT-NOVPN`)
мигрируются деплоем: привязки → NO-VPN, объекты удаляются (см.
[operations.md](operations.md)).

## 🔍 Проверка

```bash
kgate policy list                  # устройства + сегменты + политики (живая таблица)
kgate policy segments              # сегменты с числом устройств
ndmc -c "show ip hotspot"          # первоисточник привязок (running-config НЕ отражает host-бинды)
```

Симптом «устройство не в туннеле при поднятой Proxy0» — у него нет привязки
VPN или стоит NO-VPN (это норма дефолта, не поломка).

## ✏️ Изменение

```bash
# устройство → туннель / напрямую / снять привязку (дефолт = напрямую):
kgate policy set device <MAC|hostname> VPN
kgate policy set device <MAC|hostname> NO-VPN
kgate policy set device <MAC|hostname> none

# сегмент целиком (индивидуальные привязки перекрывают):
kgate policy set segment Bridge2 NO-VPN     # SMART всегда напрямую (IoT)
kgate policy set segment Bridge2 none

# массовые режимы:
kgate policy all-vpn                        # весь актив в туннель
kgate policy all-direct                     # снять все привязки
```

В веб-интерфейсе: **Приоритеты подключений → Применение политик** (проверяйте
результат через `kgate policy list`; веб при сохранении страницы «Приоритеты
доступов» может возвращать статический маршрут 0.0.0.0/0 Proxy0 — деплой
сносит его автоматически).

> [!WARNING]
> Галки в «Политике по умолчанию» веб-интерфейса не редактируются — это
> приоритетная модель ndm (все подключения участвуют по `ip global`
> приоритетам: Proxy0=1200, ISP=1000 в policy-v2; дефолт = ISP).
> Управление — `kgate policy`, не галки.

## 🔗 Взаимодействие со стеком kgate

- Трафик устройства с привязкой VPN → политика → tun2socks → relay → sing-box
  (RU-сплит внутри движка).
- Трафик с привязкой NO-VPN или без привязки → ISP напрямую, туннель не участвует.
- Привязки сохраняются демоном (`system configuration save`) и переживают reboot.

## 🩺 Диагностика «устройство не в туннеле»

1. `kgate status` — relay/sing-box running, Proxy0 up.
2. `kgate policy list` — у устройства пустая политика или NO-VPN?
3. Выходной IP фактически: `curl -sS https://1.1.1.1/cdn-cgi/trace | grep ip=`
   (hardware-offload Keenetic делает tcpdump слепым — верьте тестам выходного IP).
