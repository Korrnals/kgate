# Администрирование · Сегменты и политики ndm (policy-v2)

> 🔴 **Главные грабли интеграции.** Политика ndm, назначенная сегменту,
> действует на все его устройства; привязка устройства перекрывает привязку
> сегмента. Это конфигурация ndm, а не kgate.

## 🧭 Модель (policy-v2, семантика 09.11)

Деплой создаёт РОВНО ДВЕ политики:

| Политика | Состав | Поведение привязанного |
|---|---|---|
| **VPN** | permit Proxy0, запрет ISP | через туннель (таблица политики несёт дефолт Proxy0) |
| **NO-VPN** | permit ISP, запрет Proxy0 | напрямую через провайдера, туннель не участвует |

**Честный дефолт:** Proxy0 стоит в цепочке НИЖЕ провайдера (`ip global 1200`,
ISP 700; дефолт = провайдер; вынимать интерфейс из цепочки нельзя — он исчезает
из монитора/приоритетов/привязок, vol.2 приёмки 2026-11-11),
поэтому устройство/сегмент БЕЗ привязки ходит НАПРЯМУЮ. Привязка решает всё:

| Объект | Привязка | Поведение |
|---|---|---|
| устройство (host) | VPN | в туннеле при любом дефолте |
| устройство (host) | NO-VPN / без привязки | напрямую (fail-safe дом) |
| сегмент (Bridge) | VPN | весь сегмент в туннеле, кроме устройств с собственной привязкой |
| сегмент (Bridge) | NO-VPN | сегмент напрямую (IoT/гости), индивидуальные привязки перекрывают |

Segment id как его знает ndm — имя моста/точки доступа (`Bridge0`="Home",
`Bridge1`="LAN", `Bridge2`="SMART" на Ultra; видно в `show ip hotspot`).

В CLI сегмент адресуется любым из трёх поверхностей (kgate-001): ndm-имя
(`Home` — токен ndm-вербов, ровно как в running-config), id моста (`Bridge0`)
или description из веб-морды (`WLAN`). Верб всегда уходит с ndm-именем.

Legacy-эскейпы v1 (`VPN-TV`, `VPN-Laptops-Phones`, `DIRECT-NOVPN`)
мигрируются деплоем: привязки → NO-VPN, объекты удаляются (см.
[operations.md](operations.md)).

## 🔍 Проверка

```bash
kgate policy list                  # устройства + сегменты + политики (живая таблица)
kgate policy segments              # сегменты с числом устройств
ndmc -c "show ip hotspot"          # первоисточник привязок (running-config НЕ отражает host-бинды)
```

Симптом «устройство не в туннеле при поднятой Proxy0» — у него нет привязки
VPN или стоит NO-VPN (это норма дефолта, не поломка).

## ✏️ Изменение

```bash
# устройство → туннель / напрямую / снять привязку (дефолт = напрямую):
kgate policy set device <MAC|hostname> VPN
kgate policy set device <MAC|hostname> NO-VPN
kgate policy set device <MAC|hostname> none

# сегмент целиком (индивидуальные привязки перекрывают):
kgate policy set segment Bridge2 NO-VPN     # SMART всегда напрямую (IoT)
kgate policy set segment Bridge2 none

# массовые режимы:
kgate policy all-vpn                        # весь актив в туннель
kgate policy all-direct                     # снять все привязки
```

В веб-интерфейсе: **Приоритеты подключений → Применение политик** (проверяйте
результат через `kgate policy list`; веб при сохранении страницы «Приоритеты
доступов» может возвращать статический маршрут 0.0.0.0/0 Proxy0 — деплой
сносит его автоматически).

> [!WARNING]
> Галки в «Политике по умолчанию» веб-интерфейса не редактируются — это
> приоритетная модель ndm (все подключения участвуют по `ip global`
> приоритетам: Proxy0=1200 ниже ISP=700 в policy-v2; дефолт = ISP).
> Управление — `kgate policy`, не галки.

## 📜 Декларативные привязки: секция `policies` в kgate.yaml (1.8.0)

Привязки можно объявить конфигом — тогда `kgate apply` применяет их
автоматически после ndm-стадии, а `kgate destroy` снимает перед удалением
политик (re-apply после destroy восстанавливает заявленное состояние):

```yaml
policies:
  segments:            # ключ = ndm-имя интерфейса РОВНО как в running-config
    Home: VPN          #   (`policy Home VPN`), НЕ description («WLAN»)
    Bridge2: NO-VPN    # SMART всегда напрямую (IoT)
  devices:             # MAC-привязки (регистр MAC не важен)
    - mac: "54:AE:BC:9C:DE:BF"
      policy: NO-VPN
```

Семантика:

- **Идемпотентно.** Перед применением kgate читает живое состояние
  (`show running-config` — источник истины по привязкам) и исполняет
  ТОЛЬКО недостающие вербы; всё, что уже сходится, ndmc-записей не порождает
  (flash не изнашивается). Заодно гарантируется существование политик
  VPN/NO-VPN (штатно их создаёт ndm-commands.sh).
- **Логическая политика → имя политики роутера 1:1**: `VPN` → объект `VPN`
  (в веб-морде виден как «Туннель - весь трафик идет через VPN»),
  `NO-VPN` → объект `NO-VPN` («Напрямую - …»).
- **Без резолва описаний.** Ключи `segments` — ndm-имена, применяются
  напрямую. Резолвер kgate с 1.8.0 обходился из-за known bug 3de63d9e
  (пустые имена сегментов на ассоциация-рендере `show ip hotspot`);
  баг починен (kgate-001), но декларативные ключи остаются ndm-именами —
  детерминизм плана и совпадение с running-config важнее удобства.
- Device-привязка из `devices` сильнее сегментной (ndm-семантика override).
- Секция пуста или отсутствует → привязки не трогаются (fail-safe прямой
  дефолт сохранён).
- После привязок выполняется `system configuration save` — состояние
  переживает reboot.

Рабочие ndm-формы (таблица истинности 08.11, живой роутер — фикс 1.8.1):

| Операция | Рабочий верб | НЕ работает |
|---|---|---|
| сегмент bind | `ip hotspot policy <SEG> <POL>` | `ip hotspot <SEG> policy <POL>` — «no such command» [7405600] |
| сегмент unbind | `no ip hotspot policy <SEG>` | `no ip hotspot policy <SEG> <POL>` — argument parse error [7405602] |
| host bind | `ip hotspot host <MAC> policy <NAME>` | — |
| host unbind | `no ip hotspot host <MAC> policy` | `ip hotspot host <MAC> no policy` — parse error [7405602] |

Ещё две ловушки живого ndmc: вывод несёт ANSI-префиксы `\x1b[K` (kgate
strip'ит перед парсингом — иначе план считает всё расходящимся), а exit-коды
в tty недоверительны — invalid-верб возвращается с rc=0 и вербальной ошибкой
`error[...]`, которую kgate тоже проверяет.

Императивный путь (`kgate policy set …`) остаётся рабочим; при следующем
`kgate apply` конфиг вернёт декларированное состояние — держите секцию
в актуальном виде.

## 🔗 Взаимодействие со стеком kgate

- Трафик устройства с привязкой VPN → политика → tun2socks → relay → sing-box
  (RU-сплит внутри движка).
- Трафик с привязкой NO-VPN или без привязки → ISP напрямую, туннель не участвует.
- Привязки сохраняются демоном (`system configuration save`) и переживают reboot.

## 🩺 Диагностика «устройство не в туннеле»

1. `kgate status` — relay/sing-box running, Proxy0 up.
2. `kgate policy list` — у устройства пустая политика или NO-VPN?
3. Выходной IP фактически: `curl -sS https://1.1.1.1/cdn-cgi/trace | grep ip=`
   (hardware-offload Keenetic делает tcpdump слепым — верьте тестам выходного IP).
