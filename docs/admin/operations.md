# Администрирование · Эксплуатация и диагностика

## 🔁 Повседневные операции

```bash
kgate status      # стек одним экраном (mTLS)
kgate verify      # батарея проверок + выходной IP
kgate logs        # хвост логов демона
kgate reboot      # перезагрузка роутера
```

## 🛑 Остановка и прямой доступ

`/opt/etc/init.d/S99kgate stop` **всегда опускает Proxy0** до остановки
демона: дом остаётся на прямом доступе провайдера. Остановка безопасна —
«зависшего» туннеля с мёртвым upstream, который глушил бы всю LAN, не
останется.

```sh
/opt/etc/init.d/S99kgate stop     # Proxy0 down + демон остановлен
/opt/etc/init.d/S99kgate start    # демон; туннель поднимется через ~25 с (boot_autoup)
```

Точечное переключение без остановки супервизора — `kgate toggle on|off`.

## ⏱ Что делает демон на тике (15 с)

1. sing-box жив? → нет: рестарт с бэкоффом (5→30 с), `RLIMIT_NOFILE` наследуется.
2. DNS-jump `SBREDIRECT` в nat на месте? → нет: переприменить
   (ndm пересобирает nat при любом событии интерфейса: тумблер = 3 рефреша).

Авто-подъём при старте: демон ждёт `:1080`, затем `Proxy0 up` — бут-гонка
ndm↔Entware исключена.

## 🔄 Ребут

Полная цепочка автоматическая: `S99kgate` → демон → sing-box (FD-лимит из
конфига, дефолт 8192) →
ожидание `:1080` → `Proxy0 up` → DNS-правила → mTLS API.
Состояние тумблера переживает ребут (ndm хранит enabled).
Мигания чекера ndm («lost/detected») — косметика: интерфейс держится,
маршрут не меняется.

## 💾 Бэкап и восстановление конфигов

```bash
# бэкап (с ноутбука)
ssh root@192.168.1.1 'tar -czf /tmp/kgate-etc.tgz /opt/etc/kgate /opt/etc/sing-box'
scp root@192.168.1.1:/tmp/kgate-etc.tgz .

# восстановление
scp kgate-etc.tgz root@192.168.1.1:/tmp/
ssh root@192.168.1.1 'tar -xzf /tmp/kgate-etc.tgz -C / && /opt/etc/init.d/S99kgate restart'
```

Что защищаем: `/opt/etc/kgate/kgate.yaml`, `/opt/etc/sing-box/config.json`,
сертификаты (`web_root`). Снимайте копию перед любой пакетной операцией —
правило и ловушки старых пакетов описаны в [releases.md](releases.md)
(пакетное обновление). Живые конфиги не принадлежат пакету ≥ 1.1.2 —
`opkg remove` их не удаляет, поэтому бэкап + ручная зачистка — стандартная пара.

## 🔘 Тумблер в веб-интерфейсе vs CLI

Механика (установлена экспериментально 06.11, см. полный разбор в
kgate-session-reports/tumbler-verdict.md): переключатель на карточке HYST VPN
читает **конфиг-вью** (`show.sc.interface` → `dto.sc.up`) — персистентный
«узел намерения» `up`, а не runtime-состояние (зелёный бейдж «ПОДКЛЮЧЕНО»
живёт по runtime `show.interface` — отсюда «серый тумблер + зелёный статус +
рабочий туннель» в одном кадре). Для объекта, хоть раз тронутого вебом/RCI,
этот узел материализуется **только явным `system configuration save`** —
CLI-подъём его не создаёт (для чисто-CLI объектов он появляется сам за
секунды — потому после свежего deploy тумблер честный, а после веб-касания
навсегда серый).

- **kgate ≥ 1.4.3 делает save сам**: deploy завершает ndm-стадию
  `system configuration save` (веб-модель рождается правильной + intent
  `up` фиксируется во flash — ОС уважает его при ребуте); destroy — save
  после удаления объектов (иначе снятое воскресает при перезагрузке).
- **Источник правды — не тумблер, а `kgate status`**: поля `proxy0` (state)
  и `singbox` (running).
- **⚠️ НЕ кликай тумблер на рабочем туннеле.** Раннее считали клик no-op —
  опровергнуто: клик по серому тумблеру шлёт RCI-запись `down` в живой
  интерфейс И СОХРАНЯЕТ её во flash (инцидент 06.11 14:29: туннель упал и
  не поднялся сам 33 минуты — saved intent «down»; поднимался вручную).
  Для переключения есть `kgate toggle off` / `kgate destroy`.
- `copy running-config startup-config` — сырая файловая копия, save-
  транзакцию не выполняет: узел в конфиг-вью не материализует.
- Не выключай тумблер для «починить интернет» при живом демоне — для этого
  есть `kgate toggle off` / `kgate destroy`; при нерабочем туннеле см.
  диагностику ниже.

## 🩺 Типовые неисправности

| 🔴 Симптом | 🟡 Причина | 🟢 Действие |
|---|---|---|
| Тумблер ON, трафик прямой | сегмент/привязка DIRECT-NOVPN у устройства | [segments-and-policies.md](segments-and-policies.md) |
| RU-сайты таймаутят при ON | слетел `bind_interface` на direct-outbound (петля tun2socks) | вернуть `bind_interface: "eth3"` в конфиг sing-box |
| зарубежные таймаутят | выходной туннель не поднялся | `kgate verify` → лог sing-box; сервер доступен? |
| DNS не резолвит | снесены DNS-правила | сторож вернёт ≤15 с; вручную `S99kgate`-цикл или `ndmc` |
| sing-box не стартует после правок | невалидный конфиг / усечённый бинарь | `sing-box check -c`; размер бинаря (`ls -la`) |
| relay паникует | зонд с некорректным телом | изолировано `recover()` — демон продолжает работу |

## 🩻 Диагностика по boot-логу

Файл: `/opt/var/log/kgate-boot.log` (stdout/stderr демона, перенаправляет
`S99kgate`). Ключевые строки:

| Строка в логе | Что значит | Действие |
|---|---|---|
| `КОНФИГ НЕ НАСТРОЕН: ... содержит плейсхолдеры (HY2_PASSWORD, hy2.example.com)` | в конфиге sing-box остались шаблонные значения | заполнить `server`/`password` ([configuration.md](configuration.md)) → `S99kgate restart` |
| `autoup: пропущен — конфиг не настроен (шаблон с плейсхолдерами), Proxy0 не трогаю` | автоподъём намеренно пропущен: туннель на плейсхолдерах не поднимается | заполнить конфиг, рестарт |
| `autoup: Proxy0 up (tunnel engine готов)` | движок готов, туннель включён — норма | ничего |
| `autoup: sing-box не поднялся за 60с — Proxy0 не трогаю` | движок не стартовал за 60 с | `tail /opt/var/log/singbox.log`, `sing-box check -c /opt/etc/sing-box/config.json` |

Хвост обоих логов одной командой — `kgate logs` (через mTLS).

## 🧰 Инструментальные нюансы Entware / ndm

- `iptables` — полный путь `/opt/sbin/iptables`; флаг `-S` не поддерживается → `-L -n`
- `ip rule/route` пустые в busybox → смотреть `/proc/net/route`
- `pkill`, `xargs`, `timeout` отсутствуют → kill по PID из `ps`, циклы на sleep
- правки файлов — только heredoc-stdin (`ssh 'cat > f' << 'EOF'`); busybox sed
  не разворачивает `\n` в замене и может усечь цель через `2> файл`
- потоки LAN→WAN при hardware-offload невидимы tcpdump'у — верьте тестам
  выходного IP (`curl -sS https://1.1.1.1/cdn-cgi/trace | grep ip=`)
- ndmc в PATCH clash API принимает значения в нижнем регистре (`global`/`rule`)
